## 1. 커리어 '한 번에 넣기' (2026-10-10)

### 1-1. 요청
정리해 둔 커리어 글(머리말·소개 줄·섹션 제목·글머리 없는 줄·탭으로 된 표·날짜 범위가 섞인 약 2,500자)을
"이 채로" 붙여 넣으면 커리어 기록에 반영되게.

### 1-2. 설계 결정
| 결정 | 이유 |
|---|---|
| AI 가 **나누기만** 하고 글은 그대로(raw), 다듬은 칸(polished)은 비움 | 사용자가 "이 채로" 원함. 다듬기는 기록마다 기존 'AI로 다듬기' |
| 새 Edge 함수 대신 `career-polish` 에 `mode: "import"` | 배포·키·한도 코드 재사용. 사용 기록 fn 이름은 `career-import` 로 따로 |
| 날짜는 모델이 "적힌 만큼"(YYYY / YYYY-MM / YYYY-MM-DD)만 주고, 첫날·말일 계산은 서버 코드(`partialDate`·`cleanImported`) | 모델이 달 마지막 날·윤년을 세다 틀리지 않게 |
| 미리보기 필수(체크·고치기·이미 있음·날짜 확인·넣지 않은 줄) | AI 가 빠뜨리거나 잘못 나눈 걸 사용자가 저장 전에 봄 |
| 'AI 가 넣지 않은 줄'은 **앱이 직접 계산**(낱말 60% 겹침) | 모델의 자기 보고보다 믿을 만함 |
| 이미 있는 기록(같은 제목+시작일, 또는 같은 내용)은 처음에 빼 둠 | 두 번 붙여 넣어도 중복 안 생기게 |

### 1-3. 모델 고르기 — Haiku 5.5 vs Sonnet 5.5 (1차, pg_net 으로 직접 호출)
같은 프롬프트, 글 3개(사용자 글 2,459자 · 마크다운 이력 · 한 줄짜리 대충 쓴 글).

| | 사용자 글 | 마크다운 | 대충 쓴 글 |
|---|---|---|---|
| Haiku 5.5 (thinking 끔) | **21개 — '수강 과목' 목록 통째로 빠뜨림**, '1학기'를 1월로 | 날짜 없는 OPIc 에 앞 줄 날짜를 지어 붙임 | 한 항목 글(text)이 빈 문자열 |
| Sonnet 5.5 (effort low) | 22개 전부, 1학기 → 3~6월 | 정상 | 정상 |

비용(토큰 기준 어림): 사용자 글 1번 — Haiku 약 2원, **Sonnet 약 43원**(입력 2,800 · 출력 2,500토큰).
드물게 쓰는 기능이고 '빠뜨리지 않기'가 중요해서 **Sonnet** 으로 결정(커리어 다듬기와 같은 이유).

### 1-4. 실패한 시도 — pg_net 시험이 결과를 망가뜨림
2차 시험(프롬프트 조금 고침)에서 Sonnet 4번 중 **2번이 망가짐**: 사용자 글에서 항목 1개만 내고 끝, 다른 글은 빈 항목 1개.

- 원인: `net.http_post` 의 body 가 **jsonb** 라서 JSON 스키마의 `properties` **키 순서가 바뀜**
  (jsonb 는 키를 길이·사전순으로 정렬 → `end, kind, text, start, title …`). 구조화 출력은 스키마 순서대로 글을 쓰므로
  '내용(text)'을 '제목'보다 먼저 쓰게 되어 불안정해짐. 실제 앱(SDK)은 코드에 적힌 순서(title 먼저) 그대로 보냄.
- 해결: **임시 Edge 함수 `career-import-eval`** 을 만들어 실제 앱과 같은 요청 모양으로 시험.
  verify_jwt 끔 + 헤더 `x-cron-secret` 가 Vault `must_cron_secret` 과 같을 때만 동작, 호출은 SQL 의 pg_net 으로(비밀값을 SQL 안에서만 꺼냄).
- 결과: 같은 조건으로 **12/12 완전**(사용자 글 22항목, 약 14초) → 프롬프트 손본 뒤 **15/15**, 학력 줄 규칙 고친 뒤 **6/6**.
- 교훈(HANDOFF 5장에도 적을 것): **스키마 순서가 중요한 구조화 출력은 pg_net 으로 시험하지 말 것.**

### 1-8. 검토 — 1차는 사용 한도로 실패, 2차 성공
- 1차(2명): 두 검토자 모두 "session limit" 으로 결과 없이 멈춤(약 20만 토큰 쓰고).
- 2차(2명 + 찾은 문제마다 반박 1명 = 18명, 약 130만 토큰, 14분): **확인 8건 / 기각 4건**.

| # | 확인된 문제 | 심각도 | 고친 방법 |
|---|---|---|---|
| 1 | 끝 날짜가 시작보다 앞(예: 12월 ~ 다음 해 1월을 같은 해로 읽음)이면 끝을 조용히 버려 **하루짜리로 저장**, 경고 없음 | 중 | 다음 해로 옮겨 보고(1년 안이면) 안 되면 버림 — 어느 쪽이든 '날짜 확인'. 프롬프트에도 "끝이 앞서면 다음 해" 규칙 |
| 2 | 원문의 **'·' 글머리표·들여쓰기를 지움**(빈 표 칸 정리 코드가 글머리표까지 지움) | 중 | 원문에 그대로 있는 줄은 손대지 않고, 가운데에 ' · ' 칸 구분이 있는 표 줄에서만 앞뒤 '·' 정리 |
| 3 | 답이 길어 끊기면(max_tokens) "6,000자씩 나눠서"라고 안내 — 이미 6,000자 아래인데 | 하 | 따로 `output_too_long` → "항목이 너무 많아요 — 반씩 나눠서" |
| 4 | 제목을 UTF-16 으로 잘라 **이모지 반쪽**이 남으면 DB 가 거절 → 같이 보낸 기록 전체 동기화 실패 | 하 | 글자(코드 포인트) 단위 자르기 `cut`/`cutChars` (서버·앱) |
| 5 | 해만 적힌 시작('2022 ~ 현재')을 '2022.01'로 보여 줌(쓴 적 없는 1월) | 하 | 이런 경우 '날짜 확인' 표시 |
| 6 | 4칸 이상 표의 머리 줄('구분·기관·취득일·비고')이 늘 '넣지 않은 줄'로 뜸 | 하 | 표의 첫 줄이고 짧은 칸·숫자 없음이면 머리로 보고 뺌(표 가운데 'OPIc · IH' 같은 줄은 계속 확인) |
| 7 | 비용 안내가 최대치를 절반으로 적음, 하루 한도 문구에 이 기능이 빠짐 | 하 | 약 20~100원, 한도 문구에 포함 |
| 8 | **공개 저장소의 시험 코드에 사용자 실제 이력(회사명·날짜 몇 개)** | 상 | 지어낸 값(○○ 면접, 2030년 날짜 등)으로 교체. 예전 커밋 기록에는 남아 있음 — 지우려면 기록을 다시 써야 해서(force push) 사용자 결정 필요 |
| + | 붙여 넣기 화면에서 목록으로 돌아갈 버튼 없음 | 하 | '취소' 버튼 |

기각된 것(반박자가 재현 못 하거나 결함 아님): 숫자만 다른 줄을 빠진 줄로 못 잡음(설계상 허용) · 시트를 닫으면 붙여 넣은 글이 사라짐(보통 동작) ·
시작만 고치면 끝 날짜는 오늘로 남음(화면에 보임) · 내용 칸에 접근성 이름 없음(요청 범위 밖).

### 1-9. 고친 뒤 실제 모델로 다시 시험(2026-10-11, 임시 함수 v3 → 시험 후 v4 로 다시 닫음)
- 사용자 글: 22항목 × 2번, 약 13초.
- 해 넘는 인턴('2024.11.25 ~ 01.17'): 모델이 끝을 2025-01-17 로 바로 줌. 예시와 같은 글로 시험하면 부풀려지므로 예시('2023.12.18 ~ 02.24')와 다른 날짜로 시험함.
- '·' 글머리표 두 줄: 그대로 남음. '2022 ~ 현재': 2022-01-01 ~ 진행 중 + 날짜 확인.
- 모델 원본 답을 **실제 서버 정리 코드(cleanImport)로 로컬에서 돌려** 확인(임시 함수는 원본 답만 돌려줌).
- 함수 다시 닫을 때 import_map_path 를 빼면 MCP 가 "import map path does not exist"(옛 버전 경로)로 거절 — `import_map_path: "deno.json"` + deno.json 같이 보내야 함.

### 6-1. 찾은 순서
1. 크론 `must-send-due`: 매분 돎, 최근 1시간 60번 모두 성공. 발송 함수 응답도 200(`{"claimed":0,"briefing":{"briefed":0,"failed":0}}`) → 서버 발송 쪽은 멀쩡.
2. `push_subscriptions`: **전체 0행**(모든 사용자). → 보낼 곳이 없음. 아침 브리핑(`claim_due_briefings`)도 이 표에서 꺼내서 같이 안 옴.
3. `notification_jobs`(14일 치만 남음): 10/21·10/30 알림이 `last_error = 'no subscriptions'` → 10/21 전에 이미 구독이 없었음.
4. `auth.sessions`: 관리자 계정에 안드로이드 크롬 세션이 살아 있고 10/30 에도 갱신 → 폰은 로그인된 채 앱을 쓰고 있었음.
5. API 기록(하루치): 최근 24시간 `push_subscriptions` 요청 0건, 폰에서 온 요청 없음(PC 만).
6. 코드: 서버는 푸시 서버가 404/410(구독 만료)이면 그 행을 지움. 앱은 열 때 **브라우저에 구독이 있을 때만** 다시 저장하고 실패는 조용히 무시 →
   구독이 한 번 죽으면(권한이 거둬졌거나·사이트 데이터가 지워졌거나·푸시 서버가 만료) 사용자가 설정에서 '이 기기 등록'을 다시 누르기 전까지 영영 안 살아남.
